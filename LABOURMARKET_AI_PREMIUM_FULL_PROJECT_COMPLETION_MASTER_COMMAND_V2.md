Required capabilities:

- Chromium, Firefox and WebKit for public critical paths where feasible;
- desktop and mobile viewports;
- authenticated worker and company states;
- trace on first retry/failure;
- HTML report;
- request failure and console error capture;
- screenshot comparison for stable critical surfaces;
- explicit back/forward/reload/deep-link checks;
- loading, empty, partial, error, retry and permission-denied states;
- five consecutive clean runs for the launch-critical suite;
- production smoke suite after every production deployment.

Minimum launch-critical scenarios:

1. landing → inline login;
2. first worker onboarding;
3. profile/CV state;
4. chat-first worker action;
5. Player Card data and responsive rendering;
6. real job discovery → result → application/status;
7. journal entry → confirmation → evidence/skill update;
8. active context switching and data isolation;
9. company onboarding/need creation when the company gate opens;
10. calendar conflict and recovery;
11. logout/session expiry/re-login;
12. browser Back/Forward and reload at every nested result depth.

Playwright traces may contain sensitive state. Store them as restricted CI artifacts with retention limits; never publish authenticated traces openly.

### 2. `@axe-core/playwright` plus manual keyboard/screen-reader checks

Use automated accessibility checks inside Playwright for critical pages and states. Automated checks are necessary but not sufficient.

Required automated coverage:

- serious/critical axe violations fail CI;
- dialog/sheet focus handling;
- landmark and heading structure;
- labels, descriptions and error associations;
- contrast for semantic and context accents;
- interactive element names;
- hidden/inert background behavior;
- keyboard reachability.

Required manual proof:

- complete critical worker path using keyboard only;
- complete company need creation using keyboard only;
- visible focus at every step;
- no keyboard trap;
- logical focus return after closing a result sheet/dialog;
- 200% zoom and narrow viewport;
- a screen-reader spot-check for login, chat result, Player Card and error state.

Do not introduce a second accessibility framework if axe plus current tooling already covers CI needs.

### 3. Lighthouse CI — performance, accessibility, best-practice and SEO regression gates

Use Lighthouse CI against production-like builds and selected public production routes. Start with measured baselines and explicit budgets; do not manipulate pages merely to chase a score.

Required public routes include at least:

- canonical landing page in active locales;
- login/entry page;
- publicly shareable worker/profile surface, if enabled;
- public job/project discovery surface;
- company entry page when enabled.

Required outputs:

- performance, accessibility, best-practices and SEO reports;
- Core Web Vitals-related lab metrics;
- JS and image budget;
- route-by-route regression comparison;
- locally retained/private CI artifacts where reports could reveal non-public data.

Initial blocking policy:

- no regression from accepted baseline without explanation;
- performance or accessibility score below the agreed launch threshold blocks the affected public route;
- large JS/image regression requires explicit evidence of user value;
- verify actual field data separately when enough traffic exists; Lighthouse lab data is not production user telemetry.

### 4. Bundle and dependency inspection

First inspect whether Next.js build output and existing analysis already provide sufficient route/bundle visibility. If not, use a scoped bundle analyzer compatible with the current Next.js version.

Required checks:

- per-route JS growth;
- duplicate packages;
- client components that could remain server-side;
- heavy chart/map/editor libraries loaded outside their use path;
- unoptimized images, fonts and locale payloads;
- accidental inclusion of server-only or secret-bearing modules in client bundles.

Every significant bundle increase must state user value and alternatives considered.

### 5. GitHub dependency governance: lockfile review, Dependabot/Renovate decision, license review

Use existing GitHub dependency tooling if already configured. Do not enable both Dependabot and Renovate for the same responsibility without a clear division.

Required launch work:

- audit direct production dependencies;
- identify known vulnerable, abandoned and duplicate dependencies;
- inspect lockfile-only changes;
- verify licenses of newly introduced dependencies;
- pin GitHub Actions to trusted versions or commit SHAs according to repository policy;
- block automatic major-version merges;
- do not bulk-upgrade unrelated dependencies during launch hardening.

### 6. Semgrep — targeted static analysis

Reuse the security audit direction already discussed and any existing Semgrep setup. Run focused rules for:

- authentication and authorization mistakes;
- unsafe redirects;
- injection and unsafe query construction;
- secret exposure;
- insecure file upload/use;
- SSRF/open-fetch patterns;
- missing validation at server actions/API boundaries;
- client trust of authorization-sensitive fields;
- logging of personal or secret data.

Do not treat a raw scanner count as truth. Triage every high/critical finding against the actual code path and document false positives.

### 7. Gitleaks — secret history and diff gate

Run a secret scan on:

- the current diff;
- the repository history according to safe repository policy;
- committed screenshots, traces, fixtures and evidence files;
- `.env*` handling and example files.

Do not print discovered secrets into logs or reports. If a real secret is found, stop exposure, rotate through the authorized owner/provider process, remove it safely and document only a redacted incident record.

### 8. Trivy — filesystem, dependency, container and IaC scan where applicable

Use Trivy only for relevant surfaces already in the project:

- repository filesystem/dependencies;
- container image if this repository produces one;
- Dockerfile or infrastructure configuration;
- exposed secret/misconfiguration checks where supported.

Do not add container infrastructure merely to use Trivy. Triage critical/high findings and record whether they are reachable in production.

### 9. OWASP ZAP Automation Framework — scoped DAST against authorized environments

Run a scoped passive/baseline scan against preview/staging or a safely authorized production target. Active attacks against production are prohibited unless separately approved and proven safe.

Scope must explicitly exclude:

- destructive endpoints;
- outbound messaging/invitations;
- billing/payment paths;
- account deletion;
- real user data mutation;
- high-volume crawling that could cause service impact.

Required findings review:

- authentication/session handling;
- security headers and CSP behavior;
- cookies;
- reflected/stored injection indications;
- unintended data exposure;
- cache behavior on private pages;
- open redirects;
- sensitive URL/query content.

### 10. Supabase-native verification and safe SQL/RLS proof

Use existing safe Supabase skills/workflows and repository migration policy. Required checks:

- migration ordering and rollback notes;
- schema drift between local/preview/production;
- RLS for worker, employer, organization and service-role boundaries;
- cross-workspace leakage tests;
- storage bucket policies and signed URL expiry;
- function/search-path and security-definer review;
- index/query review for launch-critical paths;
- no direct production mutation merely to create a screenshot.

For every RLS-sensitive launch path, prove both allowed and denied access with authorized synthetic identities.

### 11. Production error monitoring — prefer existing Vercel/Supabase telemetry; add Sentry only after audit

First prove what is already available through Vercel logs/analytics, Supabase logs and current application logging. If those do not provide actionable client/server error correlation, evaluate Sentry or an equivalent scoped error-monitoring option.

A Sentry adoption decision must include:

- free/open-source/self-hosted feasibility and operational cost;
- no billing activation;
- PII scrubbing;
- source-map protection;
- environment/release tagging;
- sampling and retention;
- owner data processing/privacy implications;
- proof that current tooling cannot meet the need simply.

Minimum observability regardless of vendor:

- release/production SHA on every error;
- route and operation ID;
- user/workspace identifiers pseudonymized or omitted;
- no CV, chat, evidence, token or private payload content in logs;
- alerting for authentication failure spikes, server error spikes and critical workflow failures;
- a tested path from alert → diagnosis → rollback/fix.

### 12. OpenTelemetry — use only if it closes a proven cross-service observability gap

Do not add distributed tracing by fashion. Evaluate it only if debugging across Next.js/Vercel, Supabase, AI calls and asynchronous operations is materially blocked.

If adopted:

- start with a narrow critical transaction;
- define trace/span naming and redaction;
- keep vendor-neutral instrumentation;
- measure overhead;
- do not expose prompts, CVs, chat content or evidence data;
- prove one incident/debugging case that became materially easier.

### 13. PostHog or equivalent product analytics — optional, consent/privacy-gated

First inventory existing analytics. Add no new product analytics until legal/privacy, consent and data-minimization requirements are understood.

If an open-source/free option such as PostHog is evaluated, it may track only product events needed for launch learning, for example:

- onboarding started/completed;
- first useful result;
- job search with/without results;
- application started/completed;
- journal entry confirmed;
- context switched;
- company need created;
- error/retry outcome.

Never capture raw chat, CV, uploaded evidence, names, contact details or sensitive employment data. Session replay is disabled by default and requires explicit owner/privacy approval.

### 14. Storybook — adopt only if the component system already benefits from it

Do not create a parallel design system or documentation project during launch. If Storybook already exists, use it to exercise:

- Player Card states;
- chat/result states;
- loading/empty/error/partial states;
- context accents;
- charts with real-shaped synthetic fixtures;

If it does not exist, only add it when it shortens visual/state testing more than the installation and maintenance cost. Playwright route-level proof remains mandatory.

### 15. Visual regression — prefer Playwright snapshots; external SaaS only with owner approval

Use Playwright screenshot assertions and committed/CI baselines for stable critical surfaces. Do not introduce Chromatic, Percy or another paid/external visual SaaS without a separate data, cost and privacy decision.

Visual proof set:

- landing/login;
- first worker state;
- Player Card complete/partial/empty/error;
- job result depth states;
- journal confirmation and updated profile;
- active context variants;
- company need and candidate result;

### 17. Link, route and visible-CTA crawler

Build or adapt the smallest repository-native checker that inventories all visible links/buttons/routes in critical public and authenticated surfaces.

It must identify:

- navigation to placeholder/preview/coming-soon surfaces;
- route redirects that lose context;

Prefer extending existing route/architecture guards over adding a large crawler dependency.

Automated tests cannot judge the entire experience. Perform structured manual/browser QA on production using synthetic authorized identities.

## Release severity and decision matrix

| Severity | Definition | Launch effect | Required response |
|---|---|---|---|
| P0 | security/privacy breach, data loss, account takeover, cross-workspace leak, production outage, destructive action | full affected launch blocked | contain, rollback/disable, fix and re-prove |
| P1 | critical public path cannot complete, dead primary CTA, deceptive data/result, unusable mobile/login/onboarding, major accessibility blocker | affected worker/company gate blocked | fix before promotion sends users to path |
| P2 | material but non-blocking UX/visual/performance defect with workaround | may launch only with recorded owner-visible risk | schedule immediate fix and monitor |
| P3 | minor polish/copy inconsistency with no workflow harm | does not block | backlog with evidence |

No severity may be lowered merely to meet the date.

## Context exhaustion protocol

When available context is becoming insufficient:

1. **Do not stop implementation merely to write a narrative summary.**
2. Finish the current atomic safe step if possible.
3. Run the minimum integrity checks required to leave the repo in a known state.
4. Commit completed coherent work; do not commit broken partial work unless the repository policy explicitly uses checkpoint commits.
5. Update the live-state and evidence files with exact facts.
6. Record the next command, not merely the next topic.
7. If the execution environment supports opening/spawning a new agent session, open it immediately and pass the continuation command below.
8. If automatic session creation is technically unavailable, output the continuation command as the final visible message so the owner can paste it into a new window. Do not claim that a new window was opened if it was not.
9. The next session must begin by reading the three state files and verifying git/production state before doing anything else.
10. Never restart the audit from zero and never repeat already proven work without a specific regression reason.
