# Data Model

Source of truth: `supabase/migrations/0001_initial_schema.sql`. Reference
configuration (skills, countries, plan tiers): `supabase/reference-data.sql`.
TypeScript mirror until the schema is applied: `apps/web/lib/supabase/types.ts`
(regenerated by `pnpm db:types`).

Every table has `id uuid pk default gen_random_uuid()` (except `profiles`
whose `id` IS the `auth.users` id, and `agency_workers` whose pk is the
composite `(agency_id, worker_id)`), `created_at`, `updated_at` (auto-bumped
by the shared `set_updated_at` trigger), and **RLS enabled**.

## Entities & relationships

| Table            | Purpose                                  | Key references |
| ---------------- | ---------------------------------------- | -------------- |
| `profiles`       | One row per `auth.users`; carries `role` | `id → auth.users` |
| `workers`        | A worker's discoverable avatar           | `profile_id → profiles` (unique) |
| `skills`         | Master trade list (reference data)       | — |
| `countries`      | Target-market lookup (reference data)¹   | — |
| `worker_skills`  | Worker↔skill with self-rating + verify   | `worker_id → workers`, `skill_id → skills` |
| `companies`      | Employer org; owned by a profile         | `profile_id → profiles` |
| `agencies`       | Staffing org; owned by a profile         | `profile_id → profiles` |
| `agency_workers` | Workers managed by an agency             | `agency_id → agencies`, `worker_id → workers` |
| `projects`       | A company's project                      | `company_id → companies` |
| `job_demands`    | Role openings within a project           | `project_id → projects` |
| `matches`        | Algorithm output: worker × job_demand    | `worker_id`, `job_demand_id` |
| `match_actions`  | Actions taken on a match                 | `match_id → matches`, `actor_id → profiles` |
| `threads`        | Conversation tied to a match             | `match_id → matches` |
| `messages`       | Messages within a thread                 | `thread_id → threads`, `sender_id → profiles` |
| `consents`       | GDPR consent audit trail                 | `profile_id → profiles` |
| `leads`          | Sales pipeline                           | `assigned_to → profiles` |
| `plans`          | Plan tiers (reference data)              | — |
| `subscriptions`  | A profile's plan subscription            | `profile_id`, `plan_id` |
| `audit_logs`     | Append-only system audit                 | `actor_id → profiles` |

¹ `countries` is **not** a §5 core entity. It was added to satisfy the §10.2
requirement that target-market country rows are loaded as reference data
(`profiles.country` / `workers.preferred_countries` store the bare codes). It
is a non-conflicting reference lookup; the decision is recorded as an ADR in
slice 7.

Roles (slice 6+, see "Slice 6 — Multi-role" below): held in
`profile_roles`; the currently-active workspace is `profiles.active_role`
∈ `worker | company | agency | customer | admin`. A `NULL` active role
is permitted transiently for a freshly-created profile before onboarding
picks one. (The pre-slice-6 single-`profiles.role` model is **superseded**
by ADR 0012; older references in this file may still mention it
historically.)

## RLS — the authoritative policy reference

**This is the most important section of this document.** RLS is the only
thing enforcing multi-tenant isolation — there is no separate API layer. The
posture is **deny-by-default**: RLS is enabled on every table and a request
sees nothing unless a policy below grants it.

### Trust model

- **Anonymous (no session):** sees only the genuinely public reference tables
  (`skills`, `countries`, `plans`). Nothing else — not even "live" projects
  (those require an authenticated session).
- **Authenticated user:** scoped by `auth.uid()` (= their `profiles.id`) and
  their `role`.
- **`service_role` key:** **bypasses RLS entirely.** This is deliberate and
  load-bearing. The matching engine, billing webhooks, public lead capture,
  and audit writes run server-side as service role and therefore have **no
  user-facing write policy** — there is intentionally no way for a normal user
  to write to `matches`, `leads`, `audit_logs`, etc. Code paths using the
  service-role client must do their own authorization first (see
  `lib/supabase/admin.ts`).

### Helper functions (all `SECURITY DEFINER`)

`SECURITY DEFINER` means these run as the function owner and bypass RLS
internally — that is what prevents infinite recursion when a `profiles`
policy needs to know the caller's role.

| Function | Returns true when… |
| -------- | ------------------ |
| `is_admin()` | caller's profile role is `admin` |
| `profile_role()` | caller's role text |
| `is_employer()` | caller's role is `company` or `agency` |
| `owns_worker(w)` | caller owns worker `w` (`workers.profile_id = auth.uid()`) |
| `owns_company(c)` | caller owns company `c` |
| `owns_agency(a)` | caller owns agency `a` |
| `can_access_match(m)` | caller is the match's worker OR the hiring company |
| `can_access_thread(t)` | caller can access the thread's match |

Admins satisfy an `is_admin()` branch in every policy below, so "admin sees
and does everything" (brief §6) holds without restating it each time.

### Per-table policies

Legend: **S**=SELECT **I**=INSERT **U**=UPDATE **D**=DELETE.

**`profiles`** — your own identity row.
- S: `id = auth.uid()` or admin.
- I: `id = auth.uid()` or admin (the `on_auth_user_created` trigger normally
  creates it; the policy is the safety net).
- U: self or admin.
- D: admin only (account teardown cascades from `auth.users`).

**`workers`** — own avatar; employers may browse the directory.
- S: own (`profile_id = auth.uid()`) **or** `is_employer()` **or** admin.
  *M0 simplification:* §5 has no per-worker visibility column, so the worker
  directory is visible to all authenticated employers. Granular per-worker
  visibility arrives with the column in M1.
- I: own **and** caller role is `worker`, or admin.
- U / D: own or admin.

**`skills`** — public reference.
- S: everyone (`true`), incl. anonymous.
- I/U/D: admin only.

**`countries`** — public reference. Same as `skills`.

**`worker_skills`** — a worker's claimed/verified skills.
- S: the owning worker, **or** `is_employer()` (so employers can assess
  candidates), or admin.
- I/U/D: owning worker or admin. (Verification by a verifier/admin is an
  M1 concern; M0 keeps writes to owner+admin.)

**`companies`** — semi-public org records (they post public work).
- S: any authenticated user (`auth.uid() is not null`).
- I: `profile_id = auth.uid()` **and** role `company`, or admin.
- U / D: owner (`profile_id = auth.uid()`) or admin.

**`agencies`** — same shape as `companies`; INSERT requires role `agency`.

**`agency_workers`** — managed-pool membership.
- S: the agency owner, **or** the worker themselves, or admin.
- I/U/D: the agency owner or admin (a worker cannot add themselves to a pool).

**`projects`**
- S: owning company, **or** admin, **or** (`status = 'live'` **and**
  authenticated). Drafts/paused/closed projects stay private to the owner.
- I/U/D: owning company (`owns_company(company_id)`) or admin.

**`job_demands`** — visibility-gated openings.
- S: owning company (via its project), **or** admin, **or** the row is
  `status='open'` and authenticated **and** (`visibility='public'` **or**
  `visibility='agencies_only'` and caller role is `agency`).
  `direct_only` demands are never browsable — surfaced only through matches.
- I/U/D: owning company (via its project) or admin.

**`matches`** — algorithm output.
- S: the match's worker **or** the hiring company (`can_access_match`), or
  admin.
- I/U/D: **admin only.** Normal matches are written by the matching engine via
  the service-role client (RLS-bypassing); there is no user write path.

**`match_actions`** — append-style action log on a match.
- S: any participant of the match, or admin.
- I: `actor_id = auth.uid()` **and** the actor participates in that match —
  you can only record *your own* action on a match you're part of.
- U/D: admin only (treated as near-immutable).

**`threads`**
- S/I/U: participants of the underlying match (`can_access_match`), or admin.
- D: admin only.

**`messages`**
- S: participants of the thread's match (`can_access_thread`), or admin.
- I: `sender_id = auth.uid()` **and** the sender participates in the thread.
- U: participants or admin (e.g. setting `read_at`).
- D: admin only.

**`consents`** — GDPR trail; must not be silently destroyed.
- S/I/U: own (`profile_id = auth.uid()`) or admin (revoke = UPDATE
  `revoked_at`, not DELETE).
- D: admin only.

**`leads`**
- All operations: admin only. Public lead capture from the marketing site
  (slice 5) writes via the **service-role** client in a server action — it
  bypasses RLS, so no anonymous INSERT policy exists (prevents spam/abuse
  through the public anon key).

**`plans`** — public pricing reference.
- S: everyone (`true`). I/U/D: admin only. Displayed prices are governed
  placeholders (`pricing.plan.*`) until the founder sets
  `price_eur_monthly`.

**`subscriptions`**
- S: own or admin.
- I/U/D: admin only (billing mutations happen via service role / webhooks).

**`audit_logs`** — append-only.
- S: admin only.
- I: admin only (writes go through the service-role client).
- U/D: **no policy at all** — the table is immutable; not even admins get an
  UPDATE/DELETE path through RLS.

### How this maps to the brief's one-line summary

> *Workers see only their own data. Companies see their own + public worker
> profiles. Agencies see their managed workers + their own demand. Admins see
> everything.*

- *Workers see only their own data* → every worker-owned table keys SELECT on
  `owns_worker`/`profile_id = auth.uid()`.
- *Companies see public worker profiles* → `workers`/`worker_skills` SELECT
  includes `is_employer()`.
- *Agencies see managed workers + own demand* → `agency_workers` (agency
  owner) + `job_demands`/`projects` ownership via `owns_company`/agency
  visibility.
- *Admins see everything* → `is_admin()` branch in every policy.

### Testing the policies

After `pnpm db:push`, verify in the Supabase SQL editor with
`set role authenticated; set request.jwt.claims = '{"sub":"<uuid>"}';` and
confirm: a worker cannot `select` another worker's `worker_skills`; an
anonymous request gets rows only from `skills`/`countries`/`plans`; a company
cannot `update` a project it doesn't own. (Automated RLS tests land with the
auth feature slice in M1.)

## Slice 6 — Multi-role + customer (migration `0003_multi_role.sql`)

Status: **applied in M1** (founder runs `pnpm db:push`, see
`docs/AUTH_SETUP.md`). ADR 0012.

- `profiles.role` (M0) is **dropped**; replaced by
  `profiles.active_role text check (active_role is null or in
  ('worker','company','agency','customer','admin'))` — which workspace
  the user currently sees.
- `profiles.onboarded_at timestamptz` — null until the first onboarding
  flow completes; used by middleware to gate `/dashboard`.
- `profile_roles (id, profile_id → profiles, role, added_at, is_active,
  role_data jsonb)` — many-to-many catalogue of every role the user
  holds, with per-role onboarding answers in `role_data`. Unique
  `(profile_id, role)`.
- RLS helpers (`profile_role()`, `is_admin()`, `is_employer()`) updated
  to read `profiles.active_role` — existing per-table policies on
  workers/companies/agencies/etc. keep working unchanged. Adding a role
  via `profile_roles` does **not** grant table access until the user
  switches into it. RBAC by `active_role`; multi-role is catalogue.
- `handle_new_user()` trigger now also inserts the matching
  `profile_roles` row from `raw_user_meta_data.role` on signup.
- RLS on `profile_roles`: self + admin for all CRUD.

The `customer` value is now legal across the schema (ADR 0007).

## Architectural sketches (NOT implemented in M0)

These are **design sketches only** — no migration is applied in M0. Each is
applied at its tagged milestone (`docs/ROADMAP.md`,
`docs/PROJECT_VISION.md` §12). Shapes are indicative, not final DDL.

### `skill_verifications` — schema **M1**, UI **M2**
Implements `PROJECT_VISION.md` §6 (the five levels) — see ADR 0009.
```
skill_verifications (
  id uuid pk,
  skill_id uuid references skills,
  profile_id uuid references profiles,
  level text check (level in ('self','work_journal','manager','client','document')),
  evidence_id uuid,            -- journal entry / document / review ref
  verified_by uuid references profiles,
  verified_at timestamptz,
  created_at, updated_at
)
```
Replaces the boolean-ish `worker_skills.verified` with an explicit,
auditable level. Colour/labels in UI derive from `level` — never "verified"
unless `level >= 'manager'` or `document`.

### `professions` + `journal_templates` + `work_journals` + `journal_entries` — **M2**
Profession-specific journals (ADR 0006, `docs/PROFESSION_TEMPLATES.md`).
```
professions (id, key, name_lt, name_en, family)
journal_templates (id, profession_id references professions, field_schema jsonb)
work_journals (id, profile_id references profiles, profession_id, project_id references projects)
journal_entries (id, work_journal_id references work_journals, payload jsonb, occurred_on date, skill_refs uuid[], evidence_ids uuid[])
```
`field_schema` is data, not code — new profession = new row, no migration
(extensibility rule).

### `service_requests` + `service_bookings` — **M3**
B2C `customer` marketplace as a parallel layer over the same worker data
(ADR 0007).
```
service_requests (id, customer_id references profiles, category, location, details jsonb, status)
service_bookings (id, service_request_id references service_requests, provider_profile_id references profiles, status, scheduled_for)
```

### `decision_queue` — **M2** (computed view)
A first-class, ranked view (not a table) of everything awaiting a human
decision (`PROJECT_VISION.md` §8 module 10): pending matches, skill
confirmations, document approvals, agency offers — ordered by urgency,
scoped by RLS to the actor who must act.

### `market_intelligence_signals` — **M4**
Captured external demand signals / external listings feeding the market
intelligence module (`PROJECT_VISION.md` §8 module 11).
```
market_intelligence_signals (id, source, region, signal_type, payload jsonb, captured_at)
```

### `team_entities` — **M2**
Team as a first-class object with its own identity (brigades, installer
teams, shifts) — `PROJECT_VISION.md` §5 object 6.
```
team_entities (id, name, owner_profile_id references profiles, company_id references companies, kind, member_profile_ids uuid[])
```

### `notifications` — schema **M2**, UI shell **M1** (slice 6)

The header `NotificationPanel` ships as an empty shell in slice 6
(typed `notifications: []` on the auth context, honest "no
notifications yet" placeholder). The table that backs it lands in M2:

```
notifications (
  id           uuid pk default gen_random_uuid(),
  profile_id   uuid references profiles(id) on delete cascade,
  role         text check (role in ('worker','company','agency','customer')),
  type         text,
  payload      jsonb,
  read_at      timestamptz,
  created_at   timestamptz not null default now()
)
```

A notification carries the `role` it belongs to. The UI is already
multi-role-aware: a notification for role Y received while the user is
in role X renders a "Switch to {Y} to view" CTA wired to the same
switch action as the `RoleSwitcher`.

### `profiles.role` extension — superseded by slice 6 (migration 0003)
The original M1 sketch (extend the check constraint to the full seven
roles) is **superseded by ADR 0012**. Slice 6 took a different shape:
`profiles.role` is dropped; `profiles.active_role` carries the current
workspace (`worker | company | agency | customer | admin`); the wider
`team_leader` / `company_manager` / `hr_personnel` roles from
`docs/ROLES.md` land when their UX is built (M2+). See "Slice 6 —
Multi-role" above.

### `companies.trust_score` (already in schema)
The `companies.trust_score int default 0` column from
`supabase/migrations/0001_initial_schema.sql` (slice 4) **powers the
`CompanyScoreRing` UI** added in 5b.3.6 (`/for-companies` demand preview).
In M0 the displayed score + breakdown are a governed placeholder
(`companies.featured.1`); post-launch the ring reads real
`companies.trust_score` with the breakdown (payment / completion / reviews
/ response) derived from real signals. Symmetric to the worker OVR.
