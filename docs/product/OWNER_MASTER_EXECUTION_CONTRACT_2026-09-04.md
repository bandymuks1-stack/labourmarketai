## 1b. Owner scale / capacity requirement (recorded 2026-09-05 — PERMANENT, SYSTEM-WIDE architecture and infrastructure constraint)

> **Clarification (owner, same day): this is NOT a Gemini- or AI-specific rule.** It is a permanent constraint for the WHOLE platform — PostgreSQL / Supabase data architecture; schema and canonical entity relationships; indexes and query design; RLS and authorization; APIs and server actions; the canonical dispatcher / action backbone; Conversation and AI (Gemini and future approved models); authentication / session handling; search; matching / ranking; World / map / geospatial queries; project operations; workforce / capacity calculations; Work Journal and evidence; Living Professional Identity / CV derivation; documents and object storage; messaging / notifications; education / student flows; company / agency / employer flows; reports and exports; real-time subscriptions; queues / background and scheduled jobs; caching; analytics / telemetry / audit / provenance; integrations; deployment / runtime architecture; database / storage / compute / network capacity planning.
>
> **DATA GROWTH MATTERS AS MUCH AS USER COUNT.** 1M people produce many millions of work records, journal entries, skills, documents, applications, assignments, messages, evidence records, project relationships, education milestones and historical state changes — judge scalability by cardinality and access patterns, not by the `users` row count. Explicitly avoid: full-table scans on user-facing hot paths; loading complete organization / project / person history unnecessarily; N+1; unbounded API responses; client-side filtering of platform-scale datasets; synchronous global recalculation; global realtime broadcasts; one permanent process / agent per user; authorization whose cost requires scanning the platform; blobs in relational rows; dependence on one application instance; small-population assumptions hidden in business logic; fixed limits that silently become product architecture. **VERIFICATION:** for material high-volume paths, when appropriate, representative synthetic / load / performance tests and query-plan inspection before scale becomes an incident (p50/p95/p99 where meaningful, query count, slow queries, index usage, DB load, memory / CPU, queue depth, storage growth, realtime fan-out, external API pressure, AI token / call cost, error / rate-limit behaviour); never invent numbers to make a test pass; set budgets only when the real path and infrastructure justify them. **ACCEPTANCE:** growth should require more capacity / better indexing / caching / partitioning / async processing / replicas / infrastructure evolution — not rebuilding the Person / Company / Project / security / action / evidence / matching / conversation architecture. No separate "scale platform", duplicate registry, duplicate database model or scale agent: the ONE canonical LabourMarket.ai world must scale.
>
> **PRODUCT SCALE TARGET.** LabourMarket.ai is not being built as a small pilot or a product for a few thousand users. Design all new and modified production capabilities so the architecture can grow to AT LEAST: 1,000,000 registered people/users; large numbers of companies, institutions, projects, jobs, work records, documents and relationships; many users belonging to multiple organizations/projects/contexts; substantial concurrent usage; international/multilingual operation; very large canonical history over time. This does NOT mean provisioning infrastructure today for 1M simultaneous users. Do not overengineer or delay current P0 delivery. It means: DO NOT introduce architectural decisions that require a fundamental rewrite when usage grows.
>
> For every meaningful backend/data/runtime implementation, consider — **1. DATA MODEL:** canonical entities stable at large cardinality; no duplicate Person/Company/Project models for scaling; high-cardinality relationships; no unbounded row scans; indexable query paths; no N+1; paginate/limit large collections; bounded reads rather than loading an entire user's/company's/project's world. **2. AUTHORIZATION / RLS:** default-deny and tenant/actor safe; never solve performance by weakening RLS; avoid authorization whose cost grows linearly across the platform; test multi-organization and high-cardinality access paths. **3. CONVERSATION / AI:** never send the user's entire canonical history/world to an LLM; retrieve only the minimum authorized context for the current action; deterministic routing stays for high-confidence cheap cases; Gemini/other paid model use bounded, rate-limited, observable, cost-aware; provider scaling under the approved shared governance/routing architecture; no per-user permanent agent/process. **4. API / EXECUTION:** stateless, horizontally scalable where practical; idempotent writes; queues/background processing for expensive async work; no request that synchronously recalculates the whole labour-market graph; no global locks or single-process assumptions. **5. REAL-TIME / EVENTS:** no broadcast of every change to every user; subscriptions scoped to actor/company/project/context; derived state incrementally updated. **6. SEARCH / MATCHING / WORLD:** no full-table client-side filtering for matching, map, people search or discovery; indexed/bounded/geospatial/search-oriented retrieval; candidate generation + bounded ranking, never every person × every opportunity synchronously. **7. FILES / EVIDENCE / JOURNAL:** files in object storage, metadata/provenance canonical; long journal/evidence histories paginated and queryable by context/time/entity; derived professional identity must not reread a person's entire history per request. **8. OBSERVABILITY / COST:** latency, errors, DB pressure, AI calls/tokens/cost, queue failures, rate limiting, expensive or high-cardinality operations stay visible. **9. INTERNATIONAL SCALE:** never assume one person has one employer, one company has one role, one project has one workflow, one country/language/regulatory context; preserve the canonical multi-context model. **10. PERFORMANCE WORK IS EVIDENCE-DRIVEN:** no speculative distributed systems, microservices, Kafka, custom databases or caching layers without demonstrated need — prefer correct canonical architecture → bounded queries → correct indexes → pagination → caching where evidence warrants → async where appropriate → measurement/load testing → horizontal scaling → infrastructure expansion when real usage requires it.
>
> **SCALE ACCEPTANCE RULE.** A capability is not rejected merely because today's infrastructure would need more capacity at 1M users. It IS architecturally unacceptable if reaching that scale would require replacing the canonical data model, security model, action backbone or core product architecture because the implementation assumed a small user population. For material new P0 implementations, check this constraint silently during design and review. Do NOT create a new SCALE module, dashboard, agent, architecture project or audit programme. Escalate only if an existing architectural decision creates a genuine scale blocker requiring a significant redesign.
